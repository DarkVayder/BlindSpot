# Blindspot Threat Model

Status: reviewed at the Stage 1 gate · Method: STRIDE per trust boundary · Last updated: 2026-10-28

This document is updated at every stage gate. Each mitigation names the stage that must
implement and test it.

## 1. Assets

| Asset                                                       | Sensitivity                                                                   |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Customer source code (worker clones, local repos)           | Critical — must never be persisted or transmitted beyond the job.             |
| GitHub App private key, webhook secret, OAuth client secret | Critical.                                                                     |
| Installation access tokens, user session tokens             | High.                                                                         |
| Analysis results (paths, metrics, author counts)            | Medium–high: paths and commit metadata can reveal unreleased product details. |
| Audit logs                                                  | Medium; integrity matters more than confidentiality.                          |

## 2. Trust boundaries

1. **Repository content → analyzer** (CLI and worker). Repos are untrusted, including the user's own (supply-chain).
2. **GitHub → webhook endpoint.** Payloads are untrusted until signature-verified, and remain untrusted _data_ afterwards.
3. **Browser → web app.** Authenticated users may attempt cross-tenant access.
4. **Worker → GitHub API.** Tokens must be scoped to one installation and repo.
5. **App → database.** Every query must be tenant-scoped.

## 3. Threats and mitigations

### 3.1 Malicious repository (boundary 1)

| Threat                                                                                                                                                                                           | Mitigation                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Stage |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----- |
| Command injection via file names, branch names, refs, or config values                                                                                                                           | Git is invoked only with `spawn` and an argv array, never a shell. Refs come from git itself (full hex hashes, validated) or are passed after `--end-of-options`, and path arguments after `--`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | 1     |
| Repo-controlled git config runs code (`core.fsmonitor`, `core.hooksPath`, `diff.external`, filters, `core.sshCommand`)                                                                           | Git runs with `-c core.fsmonitor=false -c core.hooksPath=<nonexistent dir> -c diff.external= -c protocol.allow=never -c safe.bareRepository=explicit`, plus `--no-ext-diff --no-textconv` on log. Inherited `GIT_*` variables are dropped, then `GIT_CONFIG_NOSYSTEM=1`, `GIT_TERMINAL_PROMPT=0`, `GIT_OPTIONAL_LOCKS=0` and `GIT_NO_REPLACE_OBJECTS=1` are set. A test with a malicious `core.fsmonitor` (and a positive control) verifies this. On the worker, clones use `--no-checkout` where possible, and LFS smudge and submodule recursion are disabled.                                                                                                                                                                                        | 1 / 4 |
| A `git.exe` planted in the analyzed repository is executed instead of the real git (Windows resolves the current directory first)                                                                | git is resolved to an absolute path using absolute `PATH` entries only, or `BLINDSPOT_GIT` (must be absolute). Relative and `.` entries are ignored.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | 1     |
| `blindspot.config.*` executing code                                                                                                                                                              | Config is **JSON only**, validated by Zod. A `.ts`/`.js` config is not supported, because importing it would execute repo code.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | 1     |
| A repository `blindspot.config.json` (or `package.json`) that is a symlink to a secret on the analyzing machine, whose contents then leak through a JSON parse error                             | Repository config files are opened with `lstat` and refused if they are symlinks or not regular files. They are capped at 1 MB, and parse failures report only "is not valid JSON", never the parser message, which quotes input. An explicit `--config` path chosen by the user may be a link.                                                                                                                                                                                                                                                                                                                                                                                                                                                         | 1     |
| Resource exhaustion (huge files, millions of commits, deep import chains, symlink loops, zip-bomb-like generated files)                                                                          | Per-file size cap for parsing, plus a cap on commits read (configurable). Timeouts on each git process. Symlinks are not followed. The dependency graph uses iterative traversal with cycle detection. Limits that are hit are reported as `incomplete` coverage, never silently truncated.                                                                                                                                                                                                                                                                                                                                                                                                                                                             | 1     |
| ReDoS through glob patterns in a repository-supplied `blindspot.config.json` (backtracking matchers such as minimatch or `path.matchesGlob` hung for over 2 minutes on `"*a".repeat(20) + "*b"`) | Globs are matched by Blindspot’s own matcher in `packages/core/src/glob.ts`, which uses dynamic programming in O(pattern × path) time with no backtracking. Brace expansion is capped at 64 alternatives, each glob at 500 characters and each list at 200 entries, and invalid globs are rejected at config load. Tested with the patterns that hung the backtracking matchers.                                                                                                                                                                                                                                                                                                                                                                        | 1     |
| Stack exhaustion from deeply nested source parsed with the TypeScript API                                                                                                                        | Only `RangeError` from parsing is caught. The file reports complexity and dependencies as `missing: parse_failed` and the rest of the analysis continues. Any other error is rethrown, never swallowed.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | 1     |
| Path traversal (`../`, absolute paths, case-folding collisions on Windows)                                                                                                                       | Only paths from `git ls-files -z` are used. They are resolved and must stay inside the repo root, and are normalized to POSIX form in output.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | 1     |
| Script or HTML injection into the HTML report through file paths or explanation text                                                                                                             | Every interpolated value is HTML-escaped, and control characters are shown as visible `\xNN` so a name such as `new⏎line.ts` cannot display as a different path (`& < > " '`). No repository data is placed inside `<script>` or `<style>`, so the report embeds no JSON blob. The inline script reads rows only through `dataset` and `textContent`. A meta CSP sets `default-src 'none'` and allows the one inline style and one inline script only by SHA-256 hash. There are no inline event handlers, no external URLs and no `src` attributes. Commit messages are never included. Tests render hostile paths and verify with an attribute tokenizer that no `on*` attribute appears, and that the CSP hashes match the emitted style and script. | 1     |
| Terminal escape injection through file names or messages (CSI recoloring or screen clearing, OSC 8 hyperlinks, BEL)                                                                              | All terminal output passes through `sanitizeTerminal`. An end-to-end test commits names containing newlines, tabs, CSI/OSC sequences, fake `git log` syntax and bidi overrides (written straight to git objects, so it runs on Windows too) and checks the analysis, terminal, HTML and JSON outputs, which shows every C0/C1 control character and DEL as a visible `\xNN`. ANSI color is emitted only by Blindspot itself, and only when enabled.                                                                                                                                                                                                                                                                                                     | 1     |
| Misleading paths using bidirectional overrides ("Trojan Source", for example `invoice\u202etxt.exe.ts`)                                                                                          | Bidi control characters are shown as visible `\u{…}` escapes in both terminal and HTML output. A repository-hygiene test fails if Blindspot's own sources contain literal bidi, BOM or control characters.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | 1     |
| Prompt-injection text in repo content or PR descriptions                                                                                                                                         | No LLM sees repo content in v1. Repo text is never treated as instructions or commands.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | All   |

### 3.1a Research pipeline fetching public repositories (boundary 1, plus the network)

`blindspot-research fetch` is the only code that enables a git transport. It is a separate
development tool, not part of the `blindspot` CLI.

| Threat                                                                                      | Mitigation                                                                                                                                                                                                                                                                                                         | Stage |
| ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----- |
| The network-free guarantee of the CLI is weakened by the new transport option               | The runner still sets `protocol.allow=never`. Only a caller that passes `allowHttps` adds `protocol.https.allow=always`, and only the research `fetch` does. A test confirms that the default allows no transport and the option allows only HTTPS.                                                                | 2     |
| A dataset entry pointing at a hostile host, a local path, or SSH, or smuggling a git option | Dataset URLs must match `https://github.com/<owner>/<name>.git`, and the URL is passed after `--end-of-options`. `file`, `ssh` and other transports stay blocked.                                                                                                                                                  | 2     |
| A repository id escaping the cache directory                                                | Ids must match `^[a-z0-9][a-z0-9-]{0,63}$`.                                                                                                                                                                                                                                                                        | 2     |
| Code running while a repository is cloned (checkout filters, LFS smudge, submodules, hooks) | Clones use `--no-checkout`, so nothing is written to a working tree and no filter or smudge runs. Submodules are not cloned, and hooks are disabled for every git command.                                                                                                                                         | 2     |
| A cache directory that is not what it claims to be, so git walks up into another repository | An existing cache directory must be a repository's own top level, and its `origin` must equal the dataset URL. Otherwise fetch stops.                                                                                                                                                                              | 2     |
| A huge or slow repository stalling the pipeline                                             | Every git command has a time limit (default 30 minutes), and retries are bounded (3 attempts). A failed clone is removed so a retry starts clean.                                                                                                                                                                  | 2     |
| Commit messages from public repositories (untrusted text) misused or leaked                 | Messages are read only by the research `snapshot` command, and only to apply the fixed bug-fix and revert patterns from the protocol. The patterns are linear-time regular expressions written in code, never taken from the dataset. Messages are never written to snapshot outputs, reports or the CLI's output. | 2     |

### 3.2 Webhook ingestion (boundary 2)

| Threat                                             | Mitigation                                                                                                                                          | Stage |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ----- |
| Forged events                                      | HMAC-SHA256 over the **raw** body with `X-Hub-Signature-256`, compared in constant time. The request is rejected before parsing.                    | 4     |
| Replay or duplicate delivery                       | `X-GitHub-Delivery` has a unique constraint. A duplicate returns 200 and causes no new work. Job keys are idempotent (`repo:headSha:modelVersion`). | 4     |
| Oversized or malformed payloads                    | Body size limit, Zod validation of the fields we use, and unknown events acknowledged and ignored.                                                  | 4     |
| Event for an uninstalled or suspended installation | Installation status is checked on every job. Revocation marks the installation `revoked`, cancels its jobs and schedules data deletion.             | 4     |

### 3.3 Web application (boundary 3)

| Threat                                              | Mitigation                                                                                                                                                                                        | Stage |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----- |
| Cross-tenant data access (IDOR)                     | All data access goes through a repository layer that requires an `orgId` derived from the session, never from the request. Integration tests cover cross-tenant reads and writes for every route. | 3     |
| Stale permissions (a user loses GitHub repo access) | Repo access is re-verified against GitHub on session refresh and cached for a short time.                                                                                                         | 3 / 4 |
| CSRF                                                | SameSite=Lax `__Host-` cookies. State-changing routes require POST plus an origin check.                                                                                                          | 3     |
| XSS                                                 | React escaping, no `dangerouslySetInnerHTML`, strict CSP with nonces, and security headers.                                                                                                       | 5     |
| Abuse or brute force                                | Per-IP and per-user rate limits on auth, API and webhook routes.                                                                                                                                  | 3 / 6 |

### 3.4 Secrets and tokens (boundary 4)

| Threat                  | Mitigation                                                                                                                                                                | Stage |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----- |
| Private key leak        | Provided via a secret manager or env var, never committed (`.gitignore` covers `*.pem`/`.env`), never logged, and rotation documented.                                    | 4 / 7 |
| Over-privileged token   | Installation tokens are minted per job, restricted to the single repository and the minimum permissions, and never stored.                                                | 4     |
| Token in logs or errors | A structured logger with a redaction list (`authorization`, `token`, `key`, `secret`, `cookie`, URLs with credentials). Errors are mapped to safe messages at boundaries. | 3     |

### 3.5 Data at rest (boundary 5)

| Threat                             | Mitigation                                                                                                                                                                                | Stage |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----- |
| Source code persisted accidentally | The DB schema has no column for file contents. A test asserts that analysis snapshots contain no content fields. Worker temp dirs are deleted in `finally` blocks and by a startup sweep. | 3 / 4 |
| Data retained after uninstall      | A deletion job removes all repo data within a documented window. Audit log entries are kept without repo metadata.                                                                        | 4     |
| Backup exposure                    | Managed Postgres with encryption at rest. Backups are encrypted and the restore procedure is tested.                                                                                      | 7     |

## 4. Privacy commitments enforced in code

- The CLI makes **no network calls**. A Stage 1 test runs the CLI with network access blocked and must pass.
- There is no telemetry in v1. If telemetry is ever added, it must be opt-in and exclude paths, names and contents.
- Author identities are used only to compute _counts_ and _concentration_ per file. Reports and the dashboard never rank or name individual developers.
